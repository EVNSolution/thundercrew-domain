## 1. 정보 구조

로그인 후 업무 모드를 고르고 그 공간으로 들어갑니다. **세 갈래**입니다.

```
/login  →  /select-mode  →  /delivery/*  또는  /cleaning/*  또는  /maintenance/*
```

### 배송용 `/delivery/*`

| 경로 | 메뉴 | 역할 | 레이아웃 |
| --- | --- | --- | --- |
| `/delivery/control` | 관제 | 차량이 어디 있고 무엇을 잡았나 | 관제형 |
| `/delivery/dispatch` | 배차 | 주문을 풀에 올리고 잡힘을 확인 | 표형 + 폼 |
| `/delivery/records` | 이력 | 완료된 배송과 증빙 | 표형 |
| `/delivery/master-data` | 관리 | 배송용 기준정보 | 목록+상세형 |

### 클린차량 `/cleaning/*`

| 경로 | 메뉴 | 역할 | 레이아웃 |
| --- | --- | --- | --- |
| `/cleaning/control` | 관제 | 예정 시각을 지키고 있나 | 관제형(타임라인 주) |
| `/cleaning/dispatch` | 배차 | 서비스 시각을 예약하고 배정 | 표형 + 폼 |
| `/cleaning/records` | 이력 | 예정 대비 실제, 시각 준수 | 표형 |
| `/cleaning/master-data` | 관리 | 클린차량 기준정보 | 목록+상세형 |

### 정비 `/maintenance/*` — 전 차량, 용도 무관

| 경로 | 메뉴 | 역할 | 레이아웃 |
| --- | --- | --- | --- |
| `/maintenance/vehicles` | 정비 | 차량별 정비 체크 | 목록+상세형 |

요약하면 정비 품목이 `(wheelType, engineType)`으로 결정되고 용도와 무관하며,
정비 담당자는 전체 차량을 보기 때문입니다.

### 전역 — 세 모드 하단에 공통

| 경로 | 메뉴 | 역할 | 레이아웃 |
| --- | --- | --- | --- |
| `/audit` | 감사 | 운영자가 무엇을 바꿨나 | 표형 |
| `/diagnostics` | 진단 | 시스템이 제대로 도는가 | 표형 |
| `/settings` | 설정 | 서비스 기준과 연동 | 폼형 |

### 1.1 배송과 클리닝의 근본 차이

같은 이름의 메뉴가 실제로는 다른 화면인 이유입니다.

| | 배송 | 클리닝 |
| --- | --- | --- |
| 배차 성격 | **주문 풀** — 올려두면 배송원이 잡는다 (동시 1건, 반납 가능) | **시간 예약** — 운영자가 시각을 지정한다 |
| 순서 | **없음** (동시 1건이라 논할 대상이 없음) | **예정 시각순** (손으로 매기지 않음) |
| 배차 방식 | 단일뿐 (방식 선택 UI 없음) | 순차 / 왕복 |
| 관제의 핵심 | 위치 | 예정 시각 |
| 관제 주 표현 | 지도 | 타임라인 (지도는 보조) |
| 실패 신호 | 아무도 안 잡은 주문 | 예정 시각 초과 |
| 이력 지표 | 완료 시각, 증빙 | 예정 대비 편차, 정시율 |
| 고객 알림 | 없음 | 사이트 알람 (카카오는 후속) |
| 차량 고유 장비 | 함체 | 없음 |

### 1.2 기록 성격별 배치

| 종류 | 위치 | 근거 |
| --- | --- | --- |
| 배차 이력, 완료 증빙, 배차 수정 | 각 용도 모드의 이력 | 그날의 업무 산출물 |
| 클리닝 시각 준수 | 클리닝 이력 | 클리닝 고유 지표 |
| **정비 실시 기록** | **정비 모드의 이력** | 정비 담당이 전 차량을 봄 |
| 작업 로그 (`audit_logs`) | 감사 (전역) | 행위자가 관리자 계정. 용도가 없음 |
| 단말 동기화 로그 | 진단 (전역) | 시스템 단위 |
| 텔레메트리 수집 오류 | 진단 (전역) | 같음 |
| 무결성 점검 | 진단 (전역) | 같음 |
| 미수신 차량 | 진단 (전역, 용도 컬럼) | 차량 단위라 용도 구분은 되지만 시스템 관점 |
| 재시동 알림 이력 | 진단 (전역) | 차량 이상 신호 |
| 차체 상태 이력 | 관리 > 차량 상세 | 자산 맥락 |
| 스테이션 재고 이력 | 관리 > 스테이션 상세 | 같음 |
| 라이더 교육 이력 | 관리 > 라이더 상세 | 같음 |

### 1.3 기존 경로에서의 이동

| 현재 | 이동 후 |
| --- | --- |
| `/` (운영 콘솔 단일 화면) | `/select-mode` → 각 모드 첫 화면 |
| `/management/resources` 차량·라이더·매칭 | `/{purpose}/master-data` |
| `/management/operations` 배차 패널 4개 | `/{purpose}/dispatch` |
| `/management/maintenance` | `/maintenance/vehicles` + `/maintenance/items` |
| `/management/logs`, 자원관리 작업 로그 | `/audit` |
| `/management/telemetry` | `/settings` 수집 설정 + `/diagnostics` 수집 오류 |
| (없음) | `/select-mode`, `/{purpose}/records`, `/maintenance/records`, `/diagnostics`, `/settings` 신설 |

`/overview`, `/monitoring`은 `/select-mode`로 redirect합니다.

### 1.4 스테이션은 어느 모드에 두는가

배터리 스테이션은 용도 개념이 없습니다. 배송용 전기 이륜차와 클린차량이 같은
스테이션을 씁니다.

**결정**: 양쪽 관리 화면에 같은 스테이션 목록을 노출합니다. 스테이션은
차량이 아니라 인프라이므로 소속을 나눌 대상이 아닙니다.
장비 종류·단말·권역도 같은 이유로 양쪽에서 같은 목록입니다.

용도별로 갈리는 것은 **차량, 라이더, 계약, 보험**입니다.

# 배송용

## 2. 관제 `/delivery/control`

차량이 어디 있고 무엇을 잡았는지 봅니다. **위치가 핵심이고 순서 개념이 없습니다.**

**레이아웃**: 관제형. 전체 지도가 주, 떠 있는 패널이 보조.

| 영역 | 기능 | 데이터 출처 |
| --- | --- | --- |
| KPI | 배송용 차량 수, 운행 중, 대기, 미수신 | `GET /api/v1/dashboard/map-state?purpose=DELIVERY` |
| 지도 | 차량 핀(권역 색), 스테이션 핀, 미배정 주문 핀 | 같음 |
| 권역 필터 | 권역 on/off | 로컬 |
| 차량 상세 | 상태, 배터리, 라이더, **함체 상태**, 정비 요약 | `GET /api/v1/dashboard/bike-snapshot/{id}` |
| **잡은 주문** | 이 차량이 잡은 주문. **최대 1건** (§3.1) | `GET /api/v1/dispatch-orders?bikeId=&status=ASSIGNED` |
| 미배정 주문 | 아직 아무도 안 잡은 주문. 경과 시간 | `GET /api/v1/dispatch-orders?status=OFFERED` |
| 경로 재생 | 실제 주행 궤적 | `bike-location-history.ts` |
| 시동 제어 | 원격 차단·해제 | `POST /api/v1/bikes/{id}/ignition` |
| 팁 | 지도 위 제보 | `GET/POST /api/v1/tips` |

### 2.1 앞 설계에서 제거되는 것

- 배송지 순서 카드(1·2·3) → 잡은 주문은 **한 건**뿐이라 목록도 순서도 없습니다
- "도착 예정 시각" → 경로 기반 ETA를 계산할 근거가 없습니다. 필요하면 별건입니다
- "여러 주문을 잡았을 때 무엇을 그릴지" 문제 자체가 없어졌습니다 (동시 1건)

### 2.2 검토 포인트

- 미배정 주문을 지도에 핀으로 띄울지 목록으로만 둘지.
  위치가 핵심인 업무라 핀 노출을 제안합니다
- 차량과 그 차량이 잡은 주문을 선으로 이을지. 한 건뿐이라 선을 그릴 수 있게
  됐습니다 — 앞 설계에서는 순서가 없어 불가능하다고 봤던 것이 가능해졌습니다

## 3. 배차 `/delivery/dispatch`

주문을 풀에 올리고 잡힘을 확인합니다. **운영자가 배정하지 않는 것이 기본입니다.**

**레이아웃**: 표형 3단. **주문 등록이 맨 위**, 그 아래 미배정 주문 풀, 잡힌 주문.

운영자의 주 동작은 주문을 올리는 것입니다. 등록 폼이 맨 아래 있으면
주문을 넣을 때마다 스크롤해야 합니다. 목록은 확인용이므로 아래로 내립니다.

| 순서 | 영역 | 기능 | 데이터 출처 |
| --- | --- | --- | --- |
| 1 | **주문 등록** | 건별 등록 폼 — 고객명, 연락처, 주소, 권역, 메모 | `POST /api/v1/dispatch-orders` |
| 1 | 주소 검색 | 주소 → 좌표 | NCP 지오코더 |
| 2 | **미배정 주문 풀** | 올려둔 주문. **경과 시간** 컬럼. 경과 초과는 빨강 | `GET /api/v1/dispatch-orders?status=OFFERED` |
| 2 | 방치 경보 | 설정 임계(예: 10분) 초과 주문 강조 + 알림 생성 | `notifications` |
| 2 | 직접 배정 | 방치 주문에 운영자가 라이더를 지정 | `PATCH .../{id}/assign` |
| 2 | 주문 회수 | 잘못 올린 주문을 풀에서 내림 | `DELETE .../{id}` |
| 3 | 잡힌 주문 | 차량·라이더·주소·상태·잡은 시각·풀 대기 | `GET /api/v1/dispatch-orders?status=ASSIGNED` |
| 3 | 주문 수정 | 주소·메모 변경 (이력 남음) | `PATCH /api/v1/dispatch-orders/{id}` |

### 3.1 배정 규칙 (2026-08-10 확정)

| 항목 | 결정 |
| --- | --- |
| 동시 보유 | **1건.** 처리 중인 건이 없을 때만 새로 잡을 수 있다 |
| 반납 | **가능.** 잡은 주문을 풀로 되돌릴 수 있다 |
| 마감 시각 | **없음.** 풀에 우선순위가 없다 |

**동시 1건이 순서 개념을 완전히 없앱니다.** 앞 설계는 "여러 주문을 잡되 순서는
없다"였는데, 이제 한 번에 한 건이라 순서를 논할 대상 자체가 없습니다.
`dispatch_orders.sequence`는 배송용에서 완전히 미사용입니다(클리닝 전용).

동시 1건은 "한 명이 풀을 쓸어간다"는 문제도 같이 해결합니다. 별도 상한
설정이 필요하지 않습니다.

### 3.2 배정 상태 모델

| 상태 | 의미 |
| --- | --- |
| `OFFERED` | 풀에 올라와 있음. 아무도 안 잡음 |
| `ASSIGNED` | 배송원이 잡음 (또는 운영자가 지정). 배송원당 최대 1건 |
| `DONE` | 완료 |
| `WITHDRAWN` | 운영자가 회수 |

전이:

```
등록 ──▶ OFFERED ──잡기──▶ ASSIGNED ──완료──▶ DONE
             ▲                  │
             └──── 반납 ────────┘
             │
             └──회수──▶ WITHDRAWN
```

**잡기 조건**: 그 배송원에게 `ASSIGNED` 상태 주문이 없어야 합니다.
백엔드에서 검증합니다 — 앱에서만 막으면 동시 요청으로 뚫립니다.

**반납**: `ASSIGNED` → `OFFERED`로 되돌립니다. 주문을 새로 만들지 않고 같은
주문의 상태만 바꿉니다. 대신 두 값을 남깁니다.

- `return_count` — 몇 번 반납됐는지. 반복 반납은 주소 오류·접근 불가 같은
  실제 문제의 신호이므로 운영자가 봐야 합니다
- `returned_at` — 마지막 반납 시각. 풀 대기 시간을 이 시점부터 다시 셉니다

반납된 주문의 경과 시간은 **최초 등록이 아니라 마지막 반납 시각 기준**입니다.
그러지 않으면 반납된 주문이 항상 방치로 잡혀 경보가 무의미해집니다.

`assignment_mode`는 잡힌 경로를 기록합니다.

- `OFFER` — 배송원이 스스로 잡음 (기본)
- `OPERATOR` — 방치 주문에 운영자가 지정 (예외)

260804 스펙의 `AUTO`(시스템 자동 배차)는 이번 범위에서 제외합니다.
방치 주문 처리를 운영자 지정으로 정했으므로 자동 배정 로직이 필요하지 않습니다.

### 3.3 앞 설계에서 제거되는 것

- 순차 배차 (배송용에서 삭제. 클리닝 전용)
- 배차 방식 선택 UI (단일뿐이므로 불필요)
- `sequence` 사용 (클리닝 전용)
- 배정 방식 3택 select (기본이 풀이므로 선택할 것이 없음)
- 엑셀 업로드 (건별 등록으로 확정. 필요해지면 별건)

### 3.4 검토 포인트

- 방치 임계 기본값. 설정에서 조정하되 기본 몇 분으로 둘지 (현재 10분)
- 반복 반납 주문을 자동으로 걸러낼지. `return_count`가 임계를 넘으면
  풀에서 내리고 운영자 확인을 요구하는 방식을 고려할 수 있습니다
- 반납 사유를 앱에서 받을지. 받으면 원인 분석이 쉬워지지만 배송원 입력이 늘어납니다

## 4. 이력 `/delivery/records`

완료된 배송과 증빙을 확인합니다. 읽기 전용.

**레이아웃**: 표형. 좌측 목록 / 우측 상세.

| 영역 | 기능 | 데이터 출처 |
| --- | --- | --- |
| 완료 배송 | 완료 시각, 차량, 라이더, 주소, 증빙 유무 | `GET /api/v1/dispatch-orders?status=DONE` |
| 완료 증빙 | 배송 완료 사진 | `GET .../{id}/completion-photo` |
| 주문 상세 | 등록 시각, **잡은 시각**, 완료 시각, 잡은 경로, 수정 이력 | 같음 |
| 회수된 주문 | 운영자가 내린 주문 | `?status=WITHDRAWN` |

순서 컬럼이 없습니다. 대신 **등록 → 잡힘 → 완료** 세 시각과 그 간격이
운영 지표가 됩니다.

### 4.1 검토 포인트

- 등록→잡힘 간격(풀 대기 시간)을 집계로 보여줄지. 풀 모델의 핵심 지표입니다
- 보존 기간과 페이지네이션

## 5. 관리 `/delivery/master-data`

**배송용 기준정보만** 다룹니다.

**레이아웃**: 목록+상세형. 상단 대상 탭 / 좌측 목록 / 우측 편집기.

### 5.1 용도별로 갈리는 대상

| 영역 | 하위 | 기능 |
| --- | --- | --- |

### 5.2 양쪽에서 같은 대상

| 영역 | 근거 |
| --- | --- |
| 스테이션 | 배송용과 클린차량이 같은 스테이션을 씀 |

| 단말 | 단말 자체에 용도 개념 없음 |
| 권역 | 두 업무가 같은 권역 체계를 씀 |

편집은 어느 모드에서 하든 양쪽에 반영됩니다.

### 5.3 용도 변경 = 이동

차량 상세의 용도는 select가 아닙니다.

```
용도    배송용   [클린차량으로 이동]
```

누르면 확인 다이얼로그가 뜨고, 무엇이 영향받는지 설명합니다.

- 진행 중 배차가 있으면 이동을 거부합니다
- 활성 계약의 인수방식이 인수/반납 → 직영/협력로 바뀌어야 하므로
  계약 종료 또는 인수방식 재선택을 요구합니다
- 함체 장비가 붙어 있으면 탈거를 요구합니다

이동 후 목록에서 사라지고 토스트로 안내합니다 —
"클린차량으로 이동했습니다. → 클린차량 관리에서 보기"

라이더 직무 변경도 같습니다. 진행 중 배차가 있으면 거부합니다.

### 5.4 검토 포인트

- 이동 시 활성 계약 처리. 계약 종료를 강제할지 인수방식만 바꾸게 할지.
  계약은 법적 문서라 종료 후 재계약이 안전하지만 운영 부담이 큽니다
- 잘못 등록한 차량을 이동하는 경우가 흔하면 위 제약이 너무 빡빡할 수 있습니다.
  등록 후 일정 기간(예: 24시간) 내에는 제약 없이 이동 허용을 고려

## 7. 배차 `/cleaning/dispatch`

서비스 시각을 예약하고 클리너를 배정합니다. **예약 성격입니다.**

**레이아웃**: 표형 + 폼. 상단 오늘 예약(시간순) / 하단 순차 등록.

### 7.1 순서는 시각에서 나온다

**순서를 손으로 매기지 않습니다.** 예정 시각을 넣으면 그 시각순이 곧 방문 순서입니다.

등록 폼은 차량·클리너·고객 알림을 위에 두고, 그 아래 **서비스 지점 행**을
필요한 만큼 추가합니다. 각 행은 `예정 시각 · 예상 소요 · 주소`이고
순서 번호는 시각 정렬 결과로 표시되는 **읽기 전용 값**입니다.

| 영역 | 기능 | 데이터 출처 |
| --- | --- | --- |
| 날짜 선택 | 예약 날짜 | 로컬 |
| 오늘 예약 | 예정·소요·차량·클리너·방식·지점·상태 (시간순) | `GET /api/v1/dispatch-orders` |
| 방식 선택 | **순차 / 왕복** | — |
| **순차 등록** | 차량, 클리너, 고객 알림 + 지점 행 N개(예정 시각·예상 소요·주소) | `POST /api/v1/dispatch-orders` |
| 순서 표시 | 예정 시각 정렬 결과. 읽기 전용 | 파생 |
| **시간 충돌 검사** | 같은 차량의 `예정 시각 + 예상 소요` 구간 겹침 경고 | 신규 |
| 왕복 등록 | 수거 일괄 등록 → 배송 단계 전환 | `POST /api/v1/dispatch-batches` |
| 고객 알림 | 사이트 알람 발송 | `notifications` |

### 7.2 데이터 모델에 미치는 영향

시각이 순서를 정한다는 결정이 앞 설계를 두 군데 바꿉니다.

**1. `sequence`가 파생값이 됩니다.**
260804 스펙은 `dispatch_orders.sequence`를 운영자가 매기는 순서 큐로 봤습니다.
이제는 `service_scheduled_at` 정렬 결과입니다. 두 선택지가 있습니다.

- **저장하지 않고 조회 시 정렬** — 단일 진실. 시각을 바꾸면 순서가 자동으로 따라옴.
  대신 같은 시각이 두 건이면 순서가 불안정합니다(정렬 tie-break 필요)
- **등록 시점에 계산해 저장** — 조회가 단순하지만 시각 변경 시 재계산이 필요하고
  두 값이 어긋날 수 있습니다

**저장하지 않는 쪽을 제안합니다.** tie-break는 등록 순(`created_at`)으로 둡니다.
어긋날 수 있는 값을 두 개 유지하는 비용이 더 큽니다.

**2. 단일 배차가 순차에 흡수됩니다.**
지점이 1개면 단일, 여러 개면 순차입니다. 방식을 따로 고를 이유가 없어져
등록 방식은 **순차 / 왕복** 2개가 됩니다. `dispatch_method`도 이에 맞춥니다.

| | 앞 설계 | 수정 |
| --- | --- | --- |
| 배송용 | `SINGLE` | `SINGLE` (변화 없음. 주문 풀이라 방식 개념 없음) |
| 클리닝 | `SINGLE` / `SEQUENTIAL` / `ROUND` | `SEQUENTIAL` / `ROUND` |

### 7.3 검토 포인트

- 시간 충돌을 경고로 둘지 차단으로 둘지. 현재 경고
- 종료 시각을 직접 입력받을지 예상 소요로 계산할지. 현재 소요 입력
- 예약을 며칠 앞까지 받을지
- 지점을 등록한 뒤 시각만 바꿔 순서를 재배치하는 것이 실제 운영 흐름에 맞는지.
  드래그로 순서를 바꾸고 시각이 따라오는 방식을 원할 수도 있습니다
  — 그 경우 순서가 정본이 되어 이 결정이 뒤집힙니다

운영 화면만 바뀌고 라이더가 잡을 방법이 없는 상태를 피할 수 있습니다.
